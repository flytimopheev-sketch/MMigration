# Безопасность Migration Master

Документ описывает модель угроз и меры защиты, реализованные в приложении.
Область: локальная сеть и рабочая станция пользователя. Данные не покидают
локальную сеть, облако не используется.

## 1. Принципы

1. **Никакого постоянного root.** GUI и CLI запускаются от пользователя.
   Для системных операций используется отдельный `migration-master-helper`
   через `pkexec` (PolicyKit) по белому списку; GUI вызывает его только для
   явно подтверждённых установки пакетов и настройки принтеров. Для SSH
   подключение выполняется обычным администратором по ключу, без root-входа;
   при нехватке прав используется `sudo` с паролем пользователя.
2. **Ограниченный shell на удалённой стороне.** Локальные внешние команды
   запускаются отдельными аргументами `std::process::Command`. Удалённые
   команды SSH состоят из фиксированных фрагментов, а все значения путей и
   имён пользователей экранируются `shell_quote`. Привилегированный
   apply-скрипт не читает stdin (там только пароль sudo) и не содержит
   секретов.
3. **Явное подтверждение опасных действий.** Для переноса приватных SSH-ключей,
   `authorized_keys`, установки пакетов, настройки принтеров и замены файлов
   предусмотрены отдельные флаги/галочки. dconf и cron применяются от имени
   пользователя; helper не принимает произвольные команды.
4. **Резервное копирование перед изменениями** — в GUI-мастере и CLI `restore`
   (автоматически; отключается явным `--no-backup`), а в SSH-режиме sudo —
   в `<домашний каталог>/.migration-master-backup/<id>`.
5. **Секреты не сохраняются.** Пароль архива, passphrase, пароль sudo и
   содержимое приватных ключей не пишутся в SQLite, журналы, отчёты, argv или
   файлы на приёмнике.

## 2. Шифрование и целостность

| Механизм | Реализация |
|---|---|
| Шифрование архива | `age` (scrypt/passphrase) с поддержкой armor |
| Хеширование | SHA-256 для файлов и манифеста |
| Целостность | `verify` сверяет хеш `manifest.json` и SHA-256 каждого файла |
| Сложность пароля | `security::EncryptionConfig::estimate_strength` (оценка и метка) |

Пароль можно передать через `--ask-passphrase` (интерактивный ввод),
`--passphrase-file` или `--passphrase`. Последний способ виден в `ps` и
остаётся в истории оболочки, поэтому для секретов используйте первые два или
поле GUI. Пароль **нигде не сохраняется**. Восстановление зашифрованного
архива без пароля невозможно.

```bash
migration-master verify profile.rmm --ask-passphrase
migration-master verify profile.rmm --passphrase-file ~/.rmm-pass
```

## 3. Path traversal

Все пути, извлекаемые из архива, проходят через
`security::sanitize_relative_path` / `safe_join` / `validate_path`:

- запрещены `..` и абсолютные пути;
- результат должен оставаться внутри целевого каталога (лексическая
  нормализация + проверка `is_within`);
- отклонённые пути фиксируются в отчёте как ошибки.

Тесты: `security::tests::*`, `backup::tests::test_create_backup_rejects_paths_outside_base`,
`archive::tests::*`.

## 4. SSH-ключи (§4)

- Приватные ключи **не переносятся без явного согласия**
  (`include_private_ssh_keys = false` по умолчанию); в архив попадают только
  публичные ключи, `config`, `known_hosts`. Включить приватные ключи и
  `authorized_keys` можно только флагами `--include-private-ssh-keys` /
  `--include-authorized-keys` или соответствующими галочками в GUI.
- Содержимое приватных ключей не выводится в журнал и отчёты
  (идентификация — по fingerprint, `security::redact_secret`).
- После восстановления права выставляются заново
  (`ssh_keys::fix_permissions`):

  | Путь | Права |
  |---|---|
  | `~/.ssh` | `0700` |
  | приватный ключ | `0600` |
  | публичный ключ | `0644` |
  | `authorized_keys` | `0600` |
  | `config` | `0600` |

- Проверка владельца: `security::is_owned_by`, `enforce_private_permissions`.
- Существующие ключи автоматически **не заменяются**; для новых рекомендуется
  Ed25519.

## 5. Привилегированные операции (§15)

`migration-master-helper` принимает только команды из белого списка и проверяет
аргументы до запуска. Основное приложение вызывает его через `pkexec` для
установки пакетов и настройки принтеров; остальные команды доступны для
обслуживания пакета.

| Команда | Проверки |
|---|---|
| `install-packages` | валидация имён пакетов, менеджер определяется автоматически |
| `configure-printers` | имя, URI и модель принтера валидируются; вызовы `lpadmin`, `cupsenable`, `cupsaccept` |
| `install-policy` | источник — существующий файл, цель — фиксированный путь `/usr/share/polkit-1/actions/...` |
| `copy-system` | белый список префиксов: `/etc/cups`, `/etc/skel`, `/usr/share/migration-master` |
| `set-mode` | белый список префиксов: `/etc/cups`, `/etc/skel`, `/home`; права ≤ `07777` |

Действия PolicyKit (белый список `polkit::ALLOWED_ACTIONS`):

```
com.redos.migration-master.helper.install-packages
com.redos.migration-master.helper.configure-printers
com.redos.migration-master.helper.apply-system-settings
```

Файл политики: `resources/com.redos.migration-master.policy`.
Тест `polkit::tests::test_shipped_policy_matches_render` гарантирует, что файл
не разошёлся с кодом.

### 5.1. Удалённая миграция с sudo

1. Подключение — `ssh` по ключу от обычного администратора. `BatchMode=yes`
   запрещает интерактивный пароль SSH; root-login не используется.
2. Preflight выполняется **без sudo** и только читает состояние: пользователь,
   домашний каталог, владелец и права целевого каталога, свободное место,
   наличие `sudo`, `rsync`, `getent` и `restorecon`.
3. Если администратор может писать в каталог и целевой пользователь совпадает
   с администратором, выбирается прямой режим. Иначе данные складываются в
   `~/.cache/migration-master/stage/<id>` с правами `0700`; staging принадлежит
   администратору и удаляется после применения или ошибки.
4. Apply-скрипт запускается как `/usr/bin/sudo /bin/bash <stage>/apply.sh`.
   Пароль передаётся только в stdin (`sudo -S -p ''`), хранится в
   `SecretString`/`Zeroizing` и очищается после использования. В GUI поле
   очищается сразу после запуска. В argv, журналах, отчётах и удалённых файлах
   пароля нет. Беспарольный режим используется только если `sudo -n true`
   действительно разрешён.
5. Apply-скрипт проверяет, что целевой каталог совпадает с домашним каталогом
   целевого пользователя из `getent passwd` с учётом `realpath`, и отклоняет
   системные каталоги и их подкаталоги (`/`, `/etc`, `/usr`, `/var`, `/boot`,
   `/tmp` и т.п.). Это не позволяет подставить `/home/../etc`,
   `/etc/cron.d` или символьную ссылку.
6. Резервная копия создаётся внутри целевого домашнего каталога с `umask 077`
   (каталоги `0700`, владелец root); путь проверяется через `realpath`. Данные
   копируются `rsync -aHAX --chown=<user>:<group>`; при `verify` добавляется
   `--checksum`. Владелец домашнего каталога восстанавливается, права `.ssh`
   выставляются `0700`/`0600`, символическая ссылка `.ssh` не разыменовывается.
   При наличии SELinux выполняется `restorecon`.
7. Ограничение: `requiretty` в sudoers несовместим с передачей пароля через
   stdin; в этом случае нужен беспарольный sudo или ручное администрирование.
   Пароль root по SSH не запрашивается и не хранится.

## 6. Журналирование и история (§16)

Таблицы SQLite: `migrations`, `migration_items`, `hosts`, `archives`,
`application_rules`, `operation_logs`, `backups`, `settings`.

**Хранится:** дата, тип, источник, цель, статус, длительность, количество файлов,
размер, ошибки, путь к отчёту.

**Не хранится:** пароли, passphrase, пароль sudo, содержимое приватных
ключей, секреты приложений. Ключи `passphrase` и `sudo_password` помечены
`skip_serializing` в `WizardConfig`; `SecretString` печатается как `***`.

## 7. Резервное копирование

Перед перезаписью существующих файлов **GUI-мастер** и CLI `restore` создают
резервную копию (`backup::BackupManager`, по умолчанию
`~/.local/share/migration-master/backups`) с манифестом и хешами; копии можно
проверить и восстановить. В CLI backup отключается только явным `--no-backup`.
В SSH-режиме sudo резервная копия создаётся на приёмнике в
`<домашний каталог>/.migration-master-backup/<id>` с правами `0700`; путь
ограничен целевым домашним каталогом и проверяется через `realpath`.
В прямом SSH-режиме автоматическая копия не создаётся: администратор пишет
в собственный каталог; для копии используйте режим sudo или сделайте её вручную.

Проверить план без изменений:

```bash
migration-master restore profile.rmm --target /home/user --dry-run   # без изменений
```

## 8. Отказоустойчивость

- Отмена длинных операций по Ctrl+C через токен (`cancel`), проверяется в рабочих циклах.
- Атомарная запись файлов (временный файл + переименование).
- `dry-run` во всех разрушающих командах (`create`, `restore`, `migrate-ssh`).
  В `create`/`restore` режим **не оставляет следов**: файлы не создаются,
  каталог назначения не создаётся, резервная копия не делается
  (`wizard::create_backup` пропускается). В `migrate-ssh` `dry-run`
  подключается по SSH и выполняет **read-only preflight** (проверка прав,
  целевого пользователя, `sudo`, `rsync`; сведения о свободном месте
  собираются, но сравниваются только перед реальной передачей). Файлы на
  приёмнике не создаются и не изменяются, пароль sudo не запрашивается.
  Единственный побочный эффект — возможная запись host key в `known_hosts`.
  В локальных `create`/`restore` проверка свободного места в `dry-run`
  выполняется по ближайшему существующему родителю, чтобы оценка работала и для
  ещё не созданного каталога. Регрессия фиксируется тестами
  `archive::tests::test_dry_run_create_and_restore` и
  `test_dry_run_space_check_uses_existing_ancestor`.
- Повторный запуск после ошибки безопасен: незавершённые архивы не попадают в историю
  со статусом «успешно».

## 9. Проверка перед выпуском

```bash
cargo clippy --all-targets -- -D warnings
cargo test --release
```

Контрольные места в коде: отсутствие `unwrap()`/`expect()` в рабочих путях,
отсутствие локального `Command::new("sh")` и `shell: true`; удалённые команды
SSH собираются только из фиксированных фрагментов с экранированием значений,
а apply-скрипт проверяется тестами `ssh_transfer::tests::test_apply_script_*`.
